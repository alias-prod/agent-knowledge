# Signed-in browser acceptance

This is an opt-in Playwright acceptance harness for a **user-approved, isolated Preview workspace**. It does not create accounts or sessions, sign in, bypass authentication, use credentials, open production, seed data, or mutate documents. It only sends the application's deterministic assistant read shortcuts with conversation history left off:

- `Open Documents`
- `Find <existing acceptance draft title>`
- `Show knowledge graph`

Each assistant shortcut creates and completes the application's normal minimal operation receipt. These are backend mutations even with conversation history off, so this is a read-command harness, not a zero-write harness. It does not request model generation, microphone access, draft approval, document editing, or other business-data mutations.

## Before running

An authorized person must manually do all of the following in an **isolated Preview deployment**, outside this harness:

1. Create or choose an isolated workspace with a distinctive name and an already-existing acceptance draft. Do not use a production or shared workspace.
2. Open the exact HTTPS Vercel Preview URL in a normal browser. The URL must be a Vercel Preview hostname containing `-git-`, for example `https://my-app-git-e2e-team.vercel.app`. Production, localhost, custom origins, paths, query strings, and hashes are rejected by the configuration.
3. Sign in normally with a user explicitly approved for that isolated workspace. Do not provide credentials to Playwright and do not automate the sign-in flow.
4. Export that already-approved browser storage state using a trusted local process. Keep it outside the repository, preferably in a private directory with restrictive permissions. The configuration also permits `playwright/.auth/`, which is ignored by Git, but an external path is preferred. Treat this JSON file as a secret because it can contain active session cookies.
5. Record the workspace display name exactly as shown by the Documents source label (`<workspace> / Workspace`) and the exact title of the existing draft.
6. Leave the signed-in actor idle from assistant activity for at least one minute before running. Do not use that actor's assistant in another tab or test run concurrently.

No fixture generated by this harness counts as acceptance evidence.

## Run

From the repository root, supply all four explicit values for one command only:

```sh
E2E_PREVIEW_BASE_URL='https://my-app-git-e2e-team.vercel.app' \
E2E_STORAGE_STATE="$HOME/.private/agent-knowledge-e2e-state.json" \
E2E_EXPECTED_WORKSPACE='E2E Isolation - 2026-10-16' \
E2E_ACCEPTANCE_DRAFT_TITLE='Acceptance Draft - Read Only' \
bun run test:e2e
```

The harness fails closed before tests run when any value is missing, the state file is absent or stored in an unapproved repository location, or the base URL is not an HTTPS Vercel Preview origin without URL credentials. It also fails when the supplied state is signed out, belongs to a different workspace, lacks the named draft, or produces a non-live workspace graph.

## Coverage and limits

The normal and reduced-motion projects run separately:

- `desktop-chromium`, Chromium with no reduced-motion preference
- `desktop-chromium-reduced`, Chromium with `prefers-reduced-motion: reduce`
- `mobile-375-chromium`, Chromium mobile emulation at a 375px viewport with touch and reduced motion enabled

The single worker waits 11 seconds before each assistant command, including the first command of each project. This keeps the nine total commands below the application's six-requests-per-60-seconds actor limit across project boundaries. Each test has a 90-second budget for pacing and navigation; UI assertion timeouts are not relaxed. Rate-limit responses are still failures, not silently retried or bypassed.

Each verifies the visible signed-in workspace label, document and graph readiness, deterministic assistant link destinations by click or keyboard, the existing draft search, reduced-motion list graph, and no horizontal document overflow. The assistant history checkbox is asserted off before every command.

Mobile emulation checks responsive browser behavior only. It is **not** acceptance on a physical phone, real mobile browser engine, mobile network, operating-system accessibility service, or device hardware. Run separate physical-device checks when those are required.

## Handling state safely

Never commit, attach, paste, or log the storage-state JSON. Revoke or expire it after the run if your identity system supports that. If a run fails at authentication or workspace verification, refresh the state manually in the intended isolated Preview workspace rather than changing the harness or attempting a login bypass.
